# 系统设计：对话式CV部署代理

## 1. 愿景与核心原则

**愿景**: 创建一个智能助手（Agent），通过自然语言引导用户完成计算机视觉（CV）任务的配置。我们希望用户感觉像在与一位领域专家对话，而不是在被动地填写一张复杂的表单。

**核心原则**: **安全与可控**。在没有得到用户明确授权（确认）的情况下，代理绝不能执行最终的关键操作——即生成部署配置文件。这是一个不可逾越的"安全护栏"，是整个系统设计的基石。

## 2. 代理（Agent）的世界观

代理在一个由其"知识"、"工具"和"记忆"构成的封闭世界中运作。

### 2.1 代理的记忆（会话状态）

对于每一次独立的对话，代理都必须实时追踪以下信息：

*   `session_id`: 当前对话的唯一标识符。
*   `current_step`: 我们正处在对话的哪个阶段？（例如：`等待模型选择`、`等待标签选择`、`等待用户确认`、`已完成`）。
*   `context`: 到目前为止已经确定了哪些信息？
    *   `selected_model_id`: 用户最终选择的模型ID。
    *   `available_labels`: 当前已选模型所支持的所有标签列表。
    *   `selected_labels`: 用户希望检测的最终标签列表。
*   `confirmation_status`: 一个布尔标志位 (`true`/`false`)，清晰地标记用户是否已给出"行动"许可。

### 2.2 代理的工具箱（可调用的函数）

代理被赋予了三个可以自主决策使用的工具：

1.  **`find_suitable_models(task_description: string)`**:
    *   **目的**: 根据用户的自然语言描述，从模型库中找出最合适的CV模型。
    *   **示例**: 用户说："我需要一个能监控人员闯入禁区的方案。" -> 代理调用 `find_suitable_models(task_description="监控人员闯入禁区")`。
    *   **返回**: 一个包含候选模型ID的列表，例如 `['yolo-v8', 'mobilenet-ssd']`。

2.  **`get_model_labels(model_id: string)`**:
    *   **目的**: 查询一个指定的模型究竟能识别哪些物体或标签。
    *   **示例**: 用户选择了 `'yolo-v8'` 模型。 -> 代理调用 `get_model_labels(model_id='yolo-v8')`。
    *   **返回**: 一个包含可检测标签的列表，例如 `['person', 'car', 'bicycle', 'dog']`。

3.  **`create_deployment_template(model_id: string, labels: list, user_has_confirmed: boolean)`**:
    *   **目的**: 生成最终部署所需的配置文件（例如JSON或YAML）。
    *   **关键规则**: 此函数被硬编码设定为：**如果 `user_has_confirmed` 参数不为 `true`，则必须执行失败并报错**。这是我们核心安全原则的最终技术实现。
    *   **示例**: 代理已收集所有信息并获得用户确认。 -> 代理调用 `create_deployment_template(model_id='yolo-v8', labels=['person'], user_has_confirmed=true)`。
    *   **返回**: 生成的配置模板字符串。

## 3. 对话流程（理想中的"快乐路径"）

一个典型的、成功的对话会像下面这样展开：

1.  **用户**: "我需要建立一个能检测火灾的摄像头。"
    *   *代理思考*: 用户提出了一个任务目标。我需要先帮他找到合适的模型。我应该使用 `find_suitable_models` 工具。
    *   **代理行动**: 调用 `find_suitable_models(task_description="检测火灾")`。
    *   **工具返回**: `['fire-detection-model-v2']`。

2.  **代理 (对用户说)**: "没问题，我找到了一个专门用于此目的的模型：`fire-detection-model-v2`。我们用这个可以吗？"
    *   *代理思考*: 模型已经初步选定，在用户确认使用前，我最好先了解下这个模型具体能干什么，以便后续引导。我应该使用 `get_model_labels` 工具。
    *   **代理行动**: 调用 `get_model_labels(model_id='fire-detection-model-v2')`。
    *   **工具返回**: `['fire', 'smoke']`。

3.  **用户**: "好的，就用它。"
    *   **代理 (对用户说)**: "太好了。这个模型可以检测 `火灾` 和 `烟雾`。请告诉我您具体关心哪些？"

4.  **用户**: "`火灾` 和 `烟雾` 我都需要。"
    *   *代理思考*: 我已经拿到了所有必要信息：模型是 `fire-detection-model-v2`，标签是 `['fire', 'smoke']`。现在，流程已经走到了最关键的"检查点"。我必须停下来，等待用户的最终确认。我需要先更新我的记忆。
    *   **记忆更新**: `selected_model_id='fire-detection-model-v2'`, `selected_labels=['fire', 'smoke']`, `current_step='等待用户确认'`。

5.  **代理 (对用户说)**: "好的，我们已经确定：您选择了模型 `fire-detection-model-v2`，需要检测的标签是 `['fire', 'smoke']`。如果信息无误，**请回复'确认'**，我将为您生成最终的部署配置。"
    *   *代理思考*: 我现在进入等待状态。在收到明确的确认指令前，我绝不调用 `create_deployment_template` 工具。

6.  **用户**: "确认。"
    *   *代理思考*: 已收到确认！现在我获得了执行最终操作的授权。我将更新记忆，并调用最后一个工具。
    *   **记忆更新**: `confirmation_status=true`。
    *   **代理行动**: 调用 `create_deployment_template(model_id='fire-detection-model-v2', labels=['fire', 'smoke'], user_has_confirmed=true)`。
    *   **工具返回**: 一个JSON/YAML格式的配置字符串。

7.  **代理 (对用户说)**: "确认收到。这是为您生成的部署模板：[展示生成的模板内容]。"

## 4. "安全护栏"：如何处理关键确认点

在用户选择完标签后的这个节点，是整个流程设计的核心，必须稳健处理各种情况。

*   **如果用户确认**: 代理按上述第6步继续执行。
*   **如果用户提出疑问**: (例如："为什么需要我确认？")，代理需要向用户解释，这是一个安全措施，为了确保最终生成的配置完全符合您的意图，避免出错。解释后，应再次请求用户确认。
*   **如果用户修改想法**: (例如："等等，我其实只需要检测`火灾`")，代理需要立刻更新自己的记忆（`selected_labels=['fire']`），然后重新总结一遍信息，并再次请求用户对新的信息进行确认。
*   **如果用户沉默或回复无关内容**: 代理在等待一两轮对话后，应主动再次提醒用户："我正在等待您的确认，以便继续为您生成配置。"

`create_deployment_template` 函数是最后一道防线。即使代理的决策逻辑出现意外，提前调用了它，函数内部的 `user_has_confirmed` 检查也会阻止任何非预期的操作。

## 5. 技术实现要点

*   **状态持久化**: 会话状态（代理的记忆）需要存储在外部，例如使用 Redis 并设置30-60分钟的过期时间（TTL），以支持无状态的API服务。
*   **大模型供应商**: 选择的大语言模型（LLM）必须支持稳定可靠的函数调用（Function Calling）功能，例如 OpenAI GPT系列、Google Gemini 或 Anthropic Claude。
*   **工具实现**: 代理的工具箱（`find_suitable_models`等函数）在后端实现为标准的API接口，代理的运行环境可以通过网络调用它们。
